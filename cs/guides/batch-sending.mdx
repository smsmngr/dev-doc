---

Endpoint `/messages` vám umožňuje sbalit až **10 objektů zpráv**, každý s až **10 příjemci**, do jednoho API volání — to je až 100 doručení příjemcům na požadavek. Je to nejefektivnější způsob pro zvýšení propustnosti odesílání. Pokud potřebujete odeslat **tisíce až statisíce zpráv**, můžete místo mnoha HTTP požadavků nahrát jeden JSONL soubor — viz [Hromadné nahrání souboru přes REST API](#hromadné-nahrání-souboru-přes-rest-api) níže.

---

## Dvě cesty hromadného odesílání

| | `POST /messages` (JSON API v2) | Nahrání souboru (`POST /messaging/url`, REST API) |
| --- | --- | --- |
| Vhodné pro | jednotky až stovky příjemců, transakční a real-time odesílání | tisíce až statisíce zpráv, kampaně |
| Na jedno volání | 10 objektů zpráv × 10 příjemců | jeden soubor, jeden objekt zprávy na řádek |
| Odpověď | synchronně `accepted` / `rejected` s `message_id` | potvrzení nahrání; výsledek každé zprávy přes webhooky |
| Plánování | `datetime` u každé zprávy | `datetime` pro celý soubor (a volitelně u každé zprávy); zrušení přes `/messaging/cancel` |

---

## Kdy použít hromadné odesílání

- **Kampaně** — odesílejte marketingový obsah seznamu odběratelů v co nejmenším počtu API volání.
- **Skupinová oznámení** — informujte tým, třídu nebo zákaznický segment jediným požadavkem.
- **Personalizované zprávy** — dejte každému objektu zprávy vlastní `body` nebo `flow` pro přizpůsobení na příjemce, bez API volání na osobu.

---

## Jak hromadné odesílání funguje

Místo odeslání jednoho objektu zprávy na `POST /message` odešlete **pole** objektů zpráv na `POST /messages`. Každý prvek pole je nezávislá zpráva s vlastním `body`, `to`, `flow`, `tag`, `callback` a `payload`.

```json Tělo požadavku
[
  {
    "body": "Ahoj Alice!",
    "to": [
      {"phone_number": "420777123456"},
      {"phone_number": "420777654321"}
    ]
  },
  {
    "body": "Ahoj Bobe!",
    "to": [
      {"phone_number": "420777111111"}
    ]
  }
]
```

<Info>Tento příklad odešle 3 zprávy (zpráva "Ahoj Alice!" bude doručena na 2 telefonní čísla, zpráva "Ahoj Bobe!" bude doručena na jedno telefonní číslo).</Info>

```bash cURL
curl -X POST https://api.smsmngr.com/v2/messages \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    {
      "body": "Ahoj Alice!",
      "to": [
        {"phone_number": "420777123456"},
        {"phone_number": "420777654321"}
      ]
    },
    {
      "body": "Ahoj Bobe!",
      "to": [{"phone_number": "420777111111"}]
    }
  ]'
```

## Formát odpovědi

Odpověď obsahuje `request_id` na nejvyšší úrovni a dvě pole — `accepted` (dva požadavky zařazené k doručení) a `rejected` (požadavky, které selhaly při validaci). Každý přijatý požadavek obsahuje `key` (index objektu zprávy v poli) a `message_id` pro sledování.

```json Odpověď
{
  "request_id": "bc36f3d1-d284-463a-921b-a3560c154649",
  "accepted": [
    {
      "key": 0,
      "message_id": "e27ff0ac-87b5-4e1d-b644-5fc6029e2a11"
    },
    {
      "key": 1,
      "message_id": "f39ab1bd-98c6-4f2e-c755-6gd7130f3b22"
    }
  ],
  "rejected": []
}
```

Pokud objekty zpráv selžou při validaci (například chybný formát telefonního čísla), objeví se v `rejected` s `key` odpovídajícím jejich pozici v poli a popisem chyby. Platné objekty zpráv ve stejném požadavku jsou i tak přijaty a zařazeny.

## Získání message ID pro jednotlivé příjemce

Každý příjemce dostane vlastní `message_id` odvozené z dávkového `message_id` pomocí přípony indexu od nuly: `-0`, `-1`, `-2` atd.

Například, u `message_id` `e27ff0ac-87b5-4e1d-b644-5fc6029e2a11` požadavku, který má dva příjemce:

| Příjemce | message\_id |
| --- | --- |
| První (`420777123456`) | `e27ff0ac-87b5-4e1d-b644-5fc6029e2a11-0` |
| Druhý (`420777654321`) | `e27ff0ac-87b5-4e1d-b644-5fc6029e2a11-1` |

Doručovací webhooky obsahují tato ID s příponou, takže můžete propojit každou událost doručení zpět na konkrétního příjemce.

## Smíšené kanály v dávce

Každý objekt zprávy v poli má vlastní nezávislé `flow`. To znamená, že můžete odeslat SMS jedné skupině a Viber zprávu (s SMS zálohou) jiné skupině ve stejném API volání.

```json Dávka smíšených kanálů
[
  {
    "body": "Flash sleva končí dnes! Navštivte example.com/sale",
    "to": [
      {"phone_number": "420777123456"},
      {"phone_number": "420777654321"}
    ],
    "tag": "promotional",
    "flow": [
      {
        "sms": {
          "sender": "MujObchod",
          "gateway": "high"
        }
      }
    ]
  },
  {
    "body": "Flash sleva končí dnes! Navštivte example.com/sale",
    "to": [
      {"phone_number": "420777111111"},
      {"phone_number": "420777222222"}
    ],
    "tag": "promotional",
    "flow": [
      {
        "viber": {
          "sender": "MujSender",
          "body": "Flash sleva končí dnes!",
          "buttons": [
            {
              "title": "Nakupovat teď",
              "url": "https://example.com/sale"
            }
          ],
          "ttl": 60
        }
      },
      {
        "sms": {
          "sender": "MujObchod",
          "gateway": "high"
        }
      }
    ]
  }
]
```

## Limity

| Dimenze | Limit |
| --- | --- |
| Objektů zpráv na volání `/messages` | 10 |
| Příjemců na objekt zprávy | 10 |
| Celkem příjemců na volání `/messages` | 100 |

<Tip>
  Pokud potřebujete oslovit více než 100 příjemců, rozdělte seznam a odešlete více volání `/messages`. U tisíců a více zpráv je jednodušší [nahrát jeden JSONL soubor](#hromadné-nahrání-souboru-přes-rest-api) — nemusíte řešit tisíce HTTP požadavků, jejich rychlost, opakování ani návratové kódy.
</Tip>

## Hromadné nahrání souboru přes REST API

Když odesíláte tisíce až statisíce zpráv, je volání `/messages` po stovkách příjemců nepraktické: musíte řídit souběžnost a rychlost požadavků, ošetřit návratový kód každého z nich a opakovat neúspěšná volání. REST API endpoint `POST /messaging/url` vám místo toho vrátí **předpodepsanou URL**, na kterou nahrajete celý seznam zpráv jako jeden **JSONL soubor** (JSON Lines — jeden objekt zprávy na řádek) jediným file uploadem. Zpracování zpráv pak probíhá na straně SmsManager.

<Note>
  Endpoint `/messaging/url` patří do [REST API](/api-reference/rest/overview), nikoli do JSON API v2. Základní URL je `https://rest-api.smsmngr.com/v1`, autentizace je stejná — hlavička `x-api-key` se stejným API klíčem.
</Note>

<Steps>
  <Step title="Připravte JSONL soubor">
    Každý řádek souboru je jeden objekt zprávy ve **stejném formátu jako u JSON API v2** — tedy stejný objekt, jaký posíláte na `POST /message` nebo jako prvek pole na `POST /messages`. Používejte kódování UTF-8, jeden JSON objekt na řádek, bez obalujícího pole a bez čárek mezi řádky.

    ```jsonl messages.jsonl
    {"body": "Ahoj Alice! Vaše objednávka je na cestě.", "to": [{"phone_number": "420777123456"}], "tag": "transactional", "callback": "https://yourapp.com/webhooks/bulk"}
    {"body": "Ahoj Bobe! Vaše objednávka je na cestě.", "to": [{"phone_number": "420777654321"}], "tag": "transactional", "callback": "https://yourapp.com/webhooks/bulk"}
    {"body": "Flash sleva končí dnes! Navštivte example.com/sale", "to": [{"phone_number": "420777111111"}, {"phone_number": "420777222222"}], "tag": "promotional", "flow": [{"sms": {"sender": "MujObchod", "gateway": "high"}}]}
    ```

    Na každém řádku můžete použít všechna pole objektu zprávy — `to` s až 10 příjemci, `flow` se smíšenými kanály, `tag`, `callback`, `payload`, `datetime` i `delivery_time`. Pro velké soubory doporučujeme gzip kompresi:

    ```bash gzip
    gzip messages.jsonl   # vytvoří messages.jsonl.gz
    ```
  </Step>
  <Step title="Získejte URL pro nahrání">
    Zavolejte `POST /messaging/url` s vlastním identifikátorem dávky a typem souboru.

    ```bash cURL
    curl -X POST https://rest-api.smsmngr.com/v1/messaging/url \
      -H "x-api-key: YOUR_API_KEY" \
      -H "Content-Type: application/json" \
      -d '{"bulk_id": "kampan-2026-09-20", "filetype": "jsonl"}'
    ```

    ```json Odpověď
    {
      "success": true,
      "url": "https://smsmngr-bulk-uploads.s3.amazonaws.com/...&X-Amz-Expires=60..."
    }
    ```

    | Pole | Povinné | Popis |
    | --- | --- | --- |
    | `bulk_id` | ano | Váš identifikátor hromadného nahrání. Použijte unikátní, popisný řetězec (např. název kampaně a datum) — slouží ke zrušení naplánovaného nahrání. |
    | `filetype` | ano | `jsonl` pro nekomprimovaný soubor, `gz` pro gzipovaný JSONL. |
    | `datetime` | ne | Naplánovaný čas zpracování souboru v UTC (ISO 8601). Bez tohoto pole se soubor zpracuje ihned po nahrání. |
  </Step>
  <Step title="Nahrajte soubor">
    Na vrácenou URL odešlete soubor metodou `PUT`. Hlavička `Content-Type` musí odpovídat zvolenému `filetype`: `application/jsonl` pro `jsonl`, `application/gzip` pro `gz`.

    ```bash cURL (JSONL)
    curl -X PUT "https://smsmngr-bulk-uploads.s3.amazonaws.com/...&X-Amz-Expires=60..." \
      -H "Content-Type: application/jsonl" \
      --data-binary @messages.jsonl
    ```

    ```bash cURL (gzip)
    curl -X PUT "https://smsmngr-bulk-uploads.s3.amazonaws.com/...&X-Amz-Expires=60..." \
      -H "Content-Type: application/gzip" \
      --data-binary @messages.jsonl.gz
    ```

    <Warning>
      Předpodepsaná URL platí jen **60 sekund**. Vyžádejte si ji až těsně před nahráním a soubor mějte připravený předem. Nahrávejte metodou `PUT` s tělem tvořeným přímo obsahem souboru — ne přes `POST` ani `multipart/form-data`. Do samotného `PUT` požadavku neposílejte `x-api-key`; oprávnění je součástí URL.
    </Warning>
  </Step>
  <Step title="Sledujte doručení přes webhooky">
    Nahraný soubor se zpracovává asynchronně — úspěšný `PUT` znamená pouze, že soubor byl přijat. Výsledek každé zprávy (přijetí, odeslání, doručení nebo odmítnutí) dostanete jako `sentMessage` webhook na `callback` uvedený u zprávy, případně na výchozí callback URL vašeho účtu. Žádný samostatný endpoint pro stav celé dávky neexistuje.

    Každý příjemce má vlastní `message_id`; u řádků s více příjemci se `message_id` odvozuje stejně jako u `/messages` — příponou indexu `-0`, `-1` atd. Podrobnosti najdete v průvodci [Webhooky](/guides/webhooks) a v konceptu [Přijetí požadavku](/concepts/request-acceptance).
  </Step>
</Steps>

### Plánování a zrušení

Pole `datetime` v těle `POST /messaging/url` naplánuje zpracování **celého souboru** na zadaný čas v UTC. Platí stejná pravidla jako pro [plánování jednotlivých zpráv](/concepts/scheduling).

```bash cURL
curl -X POST https://rest-api.smsmngr.com/v1/messaging/url \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"bulk_id": "kampan-2026-09-21", "filetype": "gz", "datetime": "2026-09-21T08:00:00Z"}'
```

Naplánované nahrání zrušíte voláním `POST /messaging/cancel` s jeho `bulk_id`:

```bash cURL
curl -X POST https://rest-api.smsmngr.com/v1/messaging/cancel \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"bulk_id": "kampan-2026-09-21"}'
```

<Note>
  Pole `datetime` uvnitř jednotlivých řádků souboru se vztahuje k dané zprávě a uplatní se při jejím zpracování. Zpracování souboru samotného řídí jen `datetime` z požadavku na URL.
</Note>

### Chyby

| Kód | Zpráva | Příčina |
| --- | --- | --- |
| `400` | `Missing 'bulk_id' or 'filetype' or 'datetime' in request data` | Chybí povinné pole nebo má `datetime` neplatný formát. |
| `400` | `Unsupported filetype` | `filetype` není `jsonl` ani `gz`. |
| `500` | `Failed to generate upload URL` | URL se nepodařilo vygenerovat — požadavek zopakujte. |

Chyby při samotném `PUT` (například vypršelá URL nebo neodpovídající `Content-Type`) vrací úložiště přímo jako HTTP chybu bez těla ve formátu SmsManager. V takovém případě si vyžádejte novou URL a nahrání zopakujte.

<Tip>
  U velkých kampaní použijte gzip (`filetype: "gz"`) — výrazně zmenší přenášený objem. Marketingové zprávy nechte ve výchozí frontě `promotional` (viz [Fronty odesílání](/concepts/sending-queues)); prioritní fronta není pro hromadné odesílání určena.
</Tip>
